1. **JWT 拦截器**（`JwtInterceptor` + `WebMvcConfig` + `UserContext`）：`Bearer token` → 解析 userId → 存 `ThreadLocal` → `afterCompletion` 清理（防内存泄漏）。
2. **鉴权策略**：GET 放行、写操作强制登录；`/api/auth`、`/api/city`、`/api/rag`、`/api/poi`、`/api/route/draft/optimize` 被 exclude。
3. **全局异常处理**（`GlobalExceptionHandler`）：`IllegalArgumentException`→400、`RuntimeException`→500、兜底 500。
4. **静态资源映射**：`/uploads/**` → 磁盘目录。
5. **Flyway**：V1 核心表 / V2 社区表 / V3 补列。

## 三、模拟面试硬核 Q&A（含行号）

> 每个亮点 2~3 个深度追问。**「指代码」** 是面试官问到时你该翻到的位置；**「标准回答」** 是可直接口头表达的话术。

### 亮点① AI 路线生成（RAG）

**Q1：向量检索为什么不用 SQL `LIKE`，非要上 Embedding + 向量库？**

- 考察点：是否理解语义检索 vs 关键字检索的本质差异。
- 标准回答：
  > `LIKE` 只能做字面匹配，用户说「出片」，POI 名字里根本没有「出片」两个字，但拙政园、平江路就是出片。所以我用 bge-m3 把「主题+体力+时长」拼成 query 向量化，再和 POI 向量在 Redis Stack 里做余弦相似度检索，召回的是「语义上相关」的 POI，而不是「名字上相关」的。
- 指代码：`RouteGenerateServiceImpl.java:38-50`（拼 query → `vectorStore.similaritySearch` Top-K）。

**Q2：向量检索只返回向量和稀疏文本，你怎么拿到完整 POI 信息？metadata 丢失怎么解决？**

- 考察点：RAG 工程里「向量召回 + 结构化反查」的标准模式，以及踩框架坑的绕坑能力。
- 标准回答：
  > Spring AI 1.0.0-M6 的 `similaritySearch` 不返回 metadata，我没法从结果里直接拿 poiId。绕的办法是：向量化时把 `poiId:123` 拼进 text 前缀（`PoiVectorServiceImpl.java:35`），检索后从 text 里用正则 `poiId:(\d+)` 提取 ID（`RouteGenerateServiceImpl.java:66-80`），再 `selectBatchIds` 回 MySQL 一次性取出完整字段（`RouteGenerateServiceImpl.java:89`）。向量库存 embedding 负责语义召回，关系库存结构化字段负责展示，职责分离。
- 指代码：`PoiVectorServiceImpl.java:35`、`RouteGenerateServiceImpl.java:66-80`、`RouteGenerateServiceImpl.java:89`。

**Q3：怎么保证 LLM 返回的是能直接落库的结构化数据？它返回 markdown 或编造 POI 怎么办？**

- 考察点：LLM 结构化输出的 Prompt 工程 + 防御性解析。
- 标准回答：
  > 两端都防。Prompt 端我写了硬约束：只能从给定 POI 列表选、不要编造新 POI、停留 30-120 分钟、返回严格 JSON 不要 markdown 代码块（`RouteGenerateServiceImpl.java:124-162`）。解析端我做了防御：先剥掉可能出现的 ``` 围栏，再用 Jackson 读树，`tip`/`photoSpot` 这种可选字段用 `has()` 容错，poiId 反查补经纬度，解析失败抛业务异常而不是返回脏数据（`RouteGenerateServiceImpl.java:165-204`）。
- 指代码：`RouteGenerateServiceImpl.java:124-162`（Prompt）、`165-204`（解析）。

### 亮点② MCP 协议接入 12306 票务

**Q1：MCP 和普通 REST 接口有什么区别？你是怎么调通的？**

- 考察点：是否真正理解 MCP = JSON-RPC 2.0 over SSE，而非「调了个 HTTP 接口」。
- 标准回答：
  > MCP 不是 REST，是 JSON-RPC 2.0 协议，传输层走 SSE。要两阶段握手：第一步 `initialize`，带上 `protocolVersion`、`capabilities`、`clientInfo`，从响应头拿到 `mcp-session-id`；第二步带这个 session 头调 `tools/call` 查 `query-ticket-price`。我没有用现成 SDK，是手写客户端，这样我完全清楚协议时序。
- 指代码：`TrainServiceImpl.java:54-84`（initialize 拿 session）、`89-117`（tools/call 带 session 头）。

**Q2：SSE 返回你怎么解析？为什么用 `byte[]` 而不是 `String.class` 接收？**

- 考察点：流式协议解析 + HTTP 响应字符集理解。
- 标准回答：
  > 返回是 `event: message\ndata: {...}\n\n` 的 SSE 格式，我按行找到 `data: ` 前缀提取 JSON（`TrainServiceImpl.java:126-134`）。用 `byte[].class` 是因为 RestTemplate 默认按 ISO-8859-1 解码，中文会乱码，我拿到字节后手动 `StandardCharsets.UTF_8` 解码（`TrainServiceImpl.java:115-116`）。而且 12306 的数据是双层 JSON：外层是 JSON-RPC，`result.content[0].text` 里还嵌了一层业务 JSON，需要二次 `readTree`（`TrainServiceImpl.java:140-147`）。
- 指代码：`TrainServiceImpl.java:115-116`（字节解码）、`126-134`（SSE 提取）、`140-147`（双层 JSON）。

**Q3：你每次查询都重新 initialize，session 能复用吗？**

- 考察点：是否知道现状的局限，以及有优化意识。
- 标准回答：
  > 当前实现是每次查询都重新握手，session 不持久（`TrainServiceImpl.java:35`），这是为了简单和正确。优化方向是缓存 sessionId + 记录过期时间，失效就重新 initialize；再配合 Redis 把车次/票价结果缓存起来（README 里「Redis 两级缓存」就是待办）。
- 指代码：`TrainServiceImpl.java:35`（每次 initialize）。

### 亮点③ TSP 路线顺序优化

**Q1：这是不是个 TSP 问题？TSP 是 NP-hard，你为什么不直接求最优解？**

- 考察点：算法素养 + 工程权衡。
- 标准回答：
  > 是，本质就是 TSP。它是 NP-hard，不能无脑全排列。我做了策略分层：节点 ≤6 用暴力全排列求全局最优，6! = 720 毫秒级算完；>6 阶乘爆炸（7! = 5040），改用贪心最近邻 O(n²) 换性能。这个「复杂度 → 阈值」的推导就是我定 6 这个分界的原因。
- 指代码：`RouteServiceImpl.java:336-340`（≤6 暴力 / >6 贪心的分支）。

**Q2：为什么用 Haversine 公式，而不是平面欧氏距离？**

- 考察点：地理计算的严谨性。
- 标准回答：
  > 经纬度是球面坐标，在城市尺度上把两点当平面算欧氏距离会失真（高纬度更明显）。我手写了 Haversine 公式，用球面三角把经纬度差转成球面距离，R 取地球半径 6371km。
- 指代码：`RouteServiceImpl.java:363-372`（haversine 实现）。

**Q3：「固定首节点」是什么意思？为什么这么设计？**

- 考察点：是否把算法和业务语义结合起来。
- 标准回答：
  > 用户一般从酒店或车站出发，起点是不该被「优化」掉的。所以我把第一个节点摘出来不参与全排列，只对剩余节点做排列（`RouteServiceImpl.java:375-376`），既贴合业务语义，又把规模从 n! 降到 (n-1)!。
- 指代码：`RouteServiceImpl.java:374-396`（bruteForceOptimize 里 `first = nodes.get(0)` 不参与排列）。

### 亮点④ 高德三方数据管道

**Q1：你这个拉取脚本重复执行，会不会产生重复数据？**

- 考察点：幂等设计。
- 标准回答：
  > 会防。入库前按 `(cityId, name)` 查重，存在就跳过（`AmapPoiFetcher.java:52-62`）。所以这个「脚本」其实是可以反复跑、越跑越全的幂等数据管道，不是一次性爬虫。
- 指代码：`AmapPoiFetcher.java:52-62`（去重入库）。

**Q2：高德有 QPS 限制，你怎么办？**

- 考察点：三方 API 限流意识。
- 标准回答：
  > 两手：一是类别之间、单条回填之间主动 `sleep`（500ms / 400ms）拉开发起间隔；二是把回填拆成「每次最多 20 条」的小批量，单次可控、失败可重试，避免长时间占用连接触发限流或超时。
- 指代码：`AmapPoiFetcher.java:64`（sleep 500）、`232`/`283`（sleep 400）、`185`（limit 20）。

**Q3：照片和高德 ID 为什么要分两步回填，不能一次拉全吗？**

- 考察点：数据管道的「断点续传」设计。
- 标准回答：
  > 因为两步依赖不同接口：没 ID 的先用 `place/around` 按坐标+名称反查 ID（`AmapPoiFetcher.java:197-202`），拿到 ID 后再用 `place/detail` 精确拉照片（`AmapPoiFetcher.java:259-262`）。拆成两步让每一步都可重入、可单独重试，比一个大事务式的一次拉全健壮得多。
- 指代码：`AmapPoiFetcher.java:178`（backfillAmapId）、`244`（refreshPhotos）。

### 亮点⑤ 社区模块多表联查 + 点赞幂等

**Q1：帖子列表会查多少张表？有没有 N+1 问题？**

- 考察点：查询优化意识，以及能否坦诚自己的短板（见技术债 4-1）。
- 标准回答（先扬后抑，主动暴露）：
  > 帖子列表要拼作者、POI、点赞数、评论数、我是否点赞。作者和 POI 我用 `selectBatchIds` 批量查，把 N 次单查合并成一次 `IN`，这一层没有 N+1（`PostServiceImpl.java:184-190`）。但坦白说，点赞数、评论数、是否点赞这三项我目前是逐条 `selectCount`，还有 3N+2 的 N+1（`PostServiceImpl.java:212-227`），正确做法是 `GROUP BY post_id` 一次聚合，或用冗余计数字段。
- 指代码：`PostServiceImpl.java:184-190`（批量查）、`212-227`（循环 count）。

**Q2：点赞在高并发下会重复吗？**

- 考察点：并发控制，先查后插的竞态（见技术债 4-2）。
- 标准回答：
  > 目前是先查后插（`PostServiceImpl.java:99-112`），单线程下幂等没问题，但高并发下两个请求同时查到「不存在」会都插入，存在竞态。正确做法是给 `(user_id, post_id)` 建唯一键，插入冲突时捕获 `DuplicateKeyException` 转成「已点赞」的友好返回，用 DB 层兜底。
- 指代码：`PostServiceImpl.java:97-112`（like 的 check-then-insert）。

**Q3：帖子图片字段为什么存 JSON 字符串，不建独立图片表？**

- 考察点：数据建模的权衡。
- 标准回答：
  > 当前场景图片只是帖子的附属展示，最多几张，存 JSON 字符串（`PostServiceImpl.java:249-269`）够用、读一次就拿全，省掉一次联查。但如果要做图片的独立检索、去重、CDN 管理，就应该抽独立表 `post_image`，这是「够用 vs 可扩展」的取舍。
- 指代码：`PostServiceImpl.java:249-269`（toJson / fromJson）。

### 逐条话术

**4-1 帖子列表 N+1**

- 现状：`toVos()` 里作者/POI 用 `selectBatchIds` 批量查是好的，但 `likeCount`/`commentCount`/`liked` 逐条 `selectCount`，N 条帖子产生约 3N 次查询。

  > 「这里我承认还有优化空间：作者和 POI 已经用 `selectBatchIds` 批量查掉了，但点赞数、评论数、是否点赞这三个字段我还是逐条 count，属于典型的 N+1。正确做法有三：① `SELECT post_id, COUNT(*) FROM post_like WHERE post_id IN (...) GROUP BY post_id` 一次聚合；② 在 `post` 表加 `like_count`/`comment_count` 冗余字段，点赞/评论时事务内同步增减；③ 高频场景把计数放 Redis，DB 异步落库。我选②+③组合，用冗余字段保证一致性，用缓存扛读。」

**4-11 Redis 运行中 `flushdb` 丢失 `poi-index` 索引（自愈）**

- 现象：联调时 `docker exec redis-cli flushdb` 清空 Redis，之后调 `init-poi-vectors` 报 `JedisDataException: poi-index: no such index`。
- 根因：Spring AI 的 `RedisVectorStore` 建索引用 `initializeSchema(true)`，但它只在 **Bean 初始化的 `afterPropertiesSet()`** 里执行一次；运行中索引被清掉后，正在运行的 Bean 不会重建。而 `add()` 只写 JSON 数据不建索引，检索时 `ftSearch` 找不到索引就炸了。
- 修复：在 `initPoiVectors()` 开头复用 `afterPropertiesSet()` 做自愈——它内部先 `ftList()` 判断，索引在就幂等跳过、不在就按原 schema 重建（维度/字段名全由 Spring AI 自动算，不会写错）。
- 话术：
  > 「这个问题是我联调时踩到的：终端 `flushdb` 清了 Redis，之后向量初始化直接报 `poi-index: no such index`。排查后定位到 Spring AI 的 `RedisVectorStore` 建索引只在 Bean 初始化的 `afterPropertiesSet()` 里执行一次，运行中索引没了不会重建，而 `add()` 只写数据不建索引。我的修复是让初始化逻辑自愈——复用 `afterPropertiesSet()`，它内部先 `ftList()` 判断、索引在就跳过、不在就重建，天然幂等。这个坑的教训是：依赖外部中间件状态的『初始化』必须幂等可重入，不能只赌『启动时建一次』，任何『先写数据后建索引』的流程都要兜住索引丢失的场景。」
- 指代码：`PoiVectorServiceImpl.java:initPoiVectors()`、`EmbeddingConfig.java:vectorStore()`。

**4-12 Spring AI 维度探测触发硅基流动限流（重写 `dimensions()`）**

- 现象：`init-poi-vectors` 报 `Error while extracting response for type OpenAiApi$EmbeddingList`。

- 话术：
  > 「这是我排查最久的一个。现象是向量初始化报 `EmbeddingList` 解析错误。我先按直觉怀疑两点：base-url 带 `/v1`、硅基流动不支持 `dimensions`。结果用 curl 直接打接口，API 是通的、响应结构和 Spring AI 的 DTO 完全匹配，两个假设全被排除。真正的问题在于：`afterPropertiesSet` 会调 `embeddingModel.dimensions()` 拿维度，而 `bge-m3` 不在 Spring AI 已知维度表，`dimensions()` 默认会额外发一次 `embed("Hello World")` 探测——在限流边缘这多余的一次请求触发了限流，返回的错误体反序列化失败就成了这个报错。修复很干净：覆盖 `dimensions()` 直接返回 1024，维度做成配置项。这个坑教会我两件事：『curl 能通但 SDK 报错』要优先怀疑限流/额度而不是配置；第三方 SDK 的隐式探测调用是隐藏的 API 消耗，维度固定的模型一定要显式声明，别让 SDK 自己去探。」
- 指代码：`EmbeddingConfig.java:embeddingModel()`、`application.yaml:citywalk.embedding.dimensions`。

**4-13 向量检索全量召回导致跨城市数据污染（召回放宽 + 精排回表）**

- 话术：
  > 「这个 bug 的现象很有意思：佛山选『美食』，生成的路线却落在广州佛山交界，还混进文化广场、宗祠这种不是餐厅的点，标题甚至写死了『苏州』。我分两层定位：第一层查数据源——高德编码里 `14` 是科教文化、`05` 才是餐饮，我的拉取器把 `140000` 错标成了餐饮，所以库里根本没餐厅；第二层查检索——向量检索是全量召回，没按 cityId 过滤，跨城市是必然。修复分三步：修正类型码并加餐饮专用拉取；向量检索 topK 放大做候选，回表 MySQL 后按实体 `cityId` 过滤（这里我踩过一个更深的坑：本想用向量元数据过滤，结果发现 RedisVectorStore 检索时只返回 content/embedding、自定义元数据不带回来，必须回表过滤）；最后 Prompt 加主题强约束。这个坑的收获是：『语义对不上』要先查数据源对不对、再查检索逻辑，别急着怪模型；向量检索要『召回放宽、精排回表』，过滤一定用可靠字段，别信向量元数据。」
